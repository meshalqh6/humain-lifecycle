# Local security model

This application is scoped to a single trusted Windows development machine. All services bind to 127.0.0.1. Login checks a salted PBKDF2-SHA256 hash (600,000 iterations). Signed eight-hour sessions use an HttpOnly SameSite=Strict cookie. Cookies are intentionally HTTP-capable for loopback development; HTTPS, secure cookies, enterprise identity, credential rotation, account recovery and a managed secret vault are required before remote deployment.

Mutating routes require a custom application header and reject unexpected browser origins. Failed login attempts are limited per process/IP. The browser stores no SMTP/database secrets. The settings endpoint returns safe configuration only. SQL parameters are hidden in driver logs; application errors return exception types or sanitized descriptions. Never include passwords in bug reports.

Authorization is enforced from users → role → permission rows. Tools perform a second permission check after strict Pydantic validation. Composite onboarding checks document.write, hr.write and email.send. Cross-user conversation access is refused. Read access currently covers the local enterprise workspace; tenant and department isolation are not implemented. Seed creates an administrator only; restricted-role tests prove denied writes.

PDFs/CSV/XLSX and model replies are untrusted. Uploads are limited to 8 MB and selected extensions; PDFs require a signature, text and at most 40 pages; workbook expanded size is capped; one-contract spreadsheets must have exactly one row. Roster imports cap at 1000 rows and preview before commit. No formulas, macros, document commands or generated Python are executed. Files are stored as bytes in PostgreSQL. OCR and antivirus scanning are not implemented. Source review remains necessary for uncertain extraction.

The model sees no filesystem shell or SQL tool and cannot alter backend policy. Prohibited employment decisions have no tools. Salary is captured from a reviewed initial contract; there is no salary-change or termination tool. Qiwa approval and real IT provisioning are unavailable. Prompt-injection resistance is provided by restricted capabilities, policy checks and review gates, not a claim that arbitrary malicious language can always be detected.

SMTP requires an approved exact recipient and approved template at send time. Sandbox additionally requires a loopback SMTP host, port 1025 and `.test` recipient. Real sending requires explicit environment authorization and STARTTLS credentials. Template text cannot be replaced by model-generated arbitrary messages. Durable outbox identity prevents routine resend; ambiguous transport failures are UNKNOWN and held for review. SMTP_ACCEPTED is not delivery confirmation. External application recipient lists are never imported.

Source configuration, original workbook contents and APPDATA state were not imported. Synthetic seed records have explicit flags. The synthetic reset command is restricted to the named local sandbox database and preserves audit records. Data retention policy, encryption at rest, backup encryption, append-only database roles, SSO, penetration testing and concurrent multi-process operation remain production hardening work.

## Administrator email settings

GET /api/settings/email requires settings.write; PUT also requires email.send. Settings persist in application_email_settings, with validated JSON configuration and a separate encrypted password. SMTP passwords use authenticated [Fernet encryption](https://cryptography.io/en/latest/fernet/); HKDF derives a separate encryption key from the high-entropy local AUTH_SECRET. Ciphertexts never leave the backend. Saved secrets are not returned, logged or copied into audit metadata; only changed field names and a password-change flag are audited. Key rotation requires re-entering the password. No external delivery is enabled by saving defaults. Real mode requires explicit authorization, configured credentials and recipient checks. Saving the global alert recipient authorizes that exact address for renewal templates only. Already prepared jobs retain their destination and are rechecked before sending.
